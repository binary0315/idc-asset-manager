# L11 DOA 需求与当前系统差距

> 对照用户提供的「L11 DOA 完整流程」需求原文（Ticketing / Inventory / Maintenance 三系统），逐条标注当前 IDC 资产管理系统的实现状态。
> 状态：**已完成** = 功能可用且与需求一致；**部分** = 有相近能力但口径或触发方式不同；**未完成** = 当前没有。
> 更新：2026-11-23。

## 总览

需求描述的是一个**到货故障（DOA）处理闭环**：监控/检测发现异常 → 自动生成工单 → 派工换件 → 库存自动出入库 → 更新 master list → 再检测。三系统靠「SN / PN + record」串联，核心约束是**换件后 SN 同时落到工单和库存**。

当前系统是一套**单机、零第三方依赖、局域网可用的台账工具**，完成度大致等于需求里 **Inventory 子系统的底座（约 1/3）**。缺的不是增删改查，而是「事件源 + 跨系统自动联动」。

| 需求条目 | 状态 | 说明 |
|---|---|---|
| 主交付清单上传表格 → 生成勾选 → 勾选后自动入库 | 已完成 | 四类 Excel 导入：上传 → 预览 → 逐行改字段/删行/恢复 → 确认写入，比"勾选"更强 |

## 已具备的通用能力（需求未明说但支撑上述功能）

- **SN 唯一性与追溯**：型号不区分大小写唯一；服务器更换历史与备件按**服务器 id** 关联，修改 SN 不丢历史。
- **删除保护**：有关联历史的物料/服务器删除需手打型号二次确认，删除前快照进回收站可原样还原。
- **幂等与并发**：网络丢响应后重试复用同一幂等键，只落一条；RMA 处置用独占事务防并发。
- **数量口径**：严格正整数、上限 1000 万、禁止负库存，超额整笔回滚。
- **权限**：管理员/协管员，查看/编辑分离，停用即注销会话。
- **开放化**：`GET /api/config` 集中返回业务口径，将来改配置字典时前端无需改动。
- **可访问性与响应式**：label 关联控件、焦点可见、toast 读屏播报、360–1280px 布局贴合、`prefers-reduced-motion`。

## 结论与建议切口

当前系统**不是**需求的实现，但可以当它的 **Inventory 底座**：台账、出入库、SN 追溯、坏件/备件状态流转这些"数据骨架"已经扎实，需求里库存部分的描述反而比现有功能简单。

若将来要向 L11 DOA 收敛，建议按此顺序：

1. **补 Inventory 的逐件 SN / CSV 导出 / 待补货占位**（底座补强，改动最小）。
2. **加工单实体与状态机**（工单号、open/verify/close、派工、班次、照片 QR），把现有"部件换件→备件登记"接成"工单换件→自动出入库"。
3. **最后做硬件自动采集与 master list 比对**（依赖 K8s、Redfish、ipmitool，与当前零依赖单机架构冲突最大，属独立工程）。

一句话：完成度约 **Inventory 底座 1/3**；工单系统与维护自动化是两片全新大陆。
